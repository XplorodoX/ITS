Systembeschreibung

Das AALeC Quiz ist ein hardwarebasiertes Multiplayer-Quizsystem für Gruppenaktivitäten und Lehrveranstaltungen.

Die Architektur verzichtet auf mobile Endgeräte der Spieler und setzt stattdessen auf dedizierte physikalische Schnittstellen und lokale Datenübertragung.

  • Physische Controller: Spieler interagieren mit Client-Geräten (AALeC V3) zur Eingabe von Antworten und Messwerten.
  • Lokale Echtzeit-Verbindung: Datenaustausch erfolgt ereignisgesteuert über ein lokales WLAN-Netzwerk mittels MQTT.
  • Entkoppeltes Backend: Ein Python-Dienst fungiert als Spielleiter und wertet Antworten und Zeitstempel aus.
  • Präsentationsschicht: Next.js-Frontend visualisiert Spielstände und Timer auf einer Projektionsfläche (Beamer).

Spielablauf

Die physischen Controller verbinden sich beim Einschalten automatisch mit dem lokalen Access Point. Sie registrieren sich beim Game Master und warten auf den Spielstart.

Sobald gestartet, werden Fragen-Metadaten parallel an alle Clients verteilt. Die Antwortdaten (Werte und Latenz in Millisekunden) werden über den Broker zurück an das Backend übermittelt.

Netzwerk- und Systemarchitektur

Das Gesamtsystem ist modular in vier funktionale Einheiten gegliedert:

  • WLAN-Access-Point: Arduino Uno (mit WiFi-Shield) oder Router stellt das lokale Netz AALeC-Quiz bereit.
  • MQTT Broker (Mosquitto): Verwaltet die Kanäle für Client-Kommunikation (TCP 1883) und Beamer-Anbindung (WebSockets 9001).
  • Python Game Master: Führt das Regelsystem aus. Verarbeitet Antworten und steuert Statusänderungen.
  • Beamer UI (Next.js): Web-Client zur Projektion des Spielzustands. Holt Daten live über MQTT-WebSockets.

Controller-Hardware (AALeC V3)

Die Client-Hardware basiert auf der Plattform ESP8266 und integriert folgende Peripheriekomponenten:

  • OLED-Display (128x64 Pixel): Textuelle Visualisierung von Spielphase, Optionen und lokalen Menüs.
  • WS2812B RGB-LEDs: 5 adressierbare LEDs zur Visualisierung verbleibender Antwortzeit (Grün-Gelb-Rot) oder Bestätigungen.
  • Drehgeber (Rotary Encoder) mit Taster: Ermöglicht Auswahl von Antwortoptionen (A-D) sowie Bestätigung (Submit).
  • Schätz-Sensorik: Analoges Potentiometer (Schätzbereiche 0-100%) und digitaler Temperatursensor (DS18B20) für Echtzeit-Messaufgaben.
  • Piezosignalgeber: Generiert Töne zur Benutzerführung und akustischen Spielrückmeldung.

Backend - Game Master

Der **Game Master** ist die zentrale Ablaufsteuerung. Er läuft als Python-Prozess und verarbeitet MQTT-Nachrichten:

WAITING ➔ QUESTION ➔ VOTING ➔ REVEAL ➔ SCORES ➔ (NEXT/ENDED)

Funktionsumfang:

  • Spielzustände: Steuert Timeouts und Phasenübergänge.
  • Verbindungsstatus: Erkennt Abmeldungen über LWT-Nachrichten (Last Will) und passt die erwartete Stimmenanzahl dynamisch an.
  • Vorzeitiger Abbruch: Schließt Abstimmungen, sobald 100% der online registrierten Clients geantwortet haben.
MCQ-Wertung
1000 Basispunkte + max. 500 Zeitbonus (linear degressiv) + Serie-Bonus (+200 pro Runde in Serie, maximal +600).
Schätzfragen
Gestufte Wertung je nach relativer Abweichung (0.0% = 1000 Pkt, <=5.0% = 800 Pkt, abnehmend bis 0 Pkt bei >30%).
Poti-Target
Lineare Punkteermittlung innerhalb des Toleranzfensters (±5%). Volle Punktzahl bei Erreichen des exakten Zielwerts.
Temp-Target
Lineare Punkteberechnung basierend auf Abweichung zum Temperatur-Zielwert innerhalb des Toleranzbereichs (±1.5°C).

Beamer-Präsentationsschicht

Die Benutzeroberfläche zur Sammelanzeige ist als Web-Applikation mit **Next.js** und **TypeScript** implementiert.

Sie projiziert den aktuellen Systemzustand für alle Spieler sichtbar auf einer Leinwand.

  • Lobby: Übersicht angemeldeter Spieler und Bereitschaftsstatus. Ermöglicht Spielstart.
  • Fragenanzeige: Darstellung der aktiven Aufgabe, Antwortoptionen und Ablaufzeit.
  • Antwortfortschritt: Live-Visualisierung der Anzahl bereits abgegebener Antworten.
  • Rangliste: Anzeige der Gesamtpunktzahlen und korrekter Serienergebnisse.

MQTT-Kommunikationsprotokoll

Der Datenaustausch erfolgt über strukturierte **JSON-Nachrichten** via MQTT. Dies ermöglicht Event-gesteuerte Nachrichtenvermittlung:

Topic Richtung Bedeutung / Payload
quiz/state GM ➔ Alle Aktueller Status (z. B. VOTING, REVEAL)
quiz/question GM ➔ Alle Metadaten der Frage (Typ, Limits, Optionen)
quiz/connect/+ AALeC ➔ GM Anmeldung eines neuen Controllers am System
quiz/answer/+ AALeC ➔ GM Gewählte Antwort und gemessene Latenzzeit
quiz/control Web ➔ GM Ablaufbefehle (starten, zurücksetzen)
JSON-Beispiel: quiz/question (Schätzung)
{
  "id": 42,
  "type": "estimate",
  "text": "Wie hoch ist der Eiffelturm in Metern?",
  "time_limit_s": 20,
  "min": 100,
  "max": 500,
  "unit": "m"
}

Inbetriebnahme & Bereitstellung

Die Bereitstellung der Serverkomponenten erfolgt containerisiert mittels **Docker Compose**:

Schritt 1
WLAN-Setup
Access Point bereitstellen: SSID AALeC-Quiz, Passwort 12345678. IP-Adresse des Host-Systems ermitteln.
Schritt 2
Firmware Flash
Broker-IP in config.h konfigurieren. Flashen der Hardware über PlatformIO (pio run -t upload).
Schritt 3
Dienste starten
Ausführen von docker compose up -d auf dem Host. Startet Mosquitto, Python GM und Next.js-Dienst.
Schritt 4
Spielsteuerung
Dashboard im Browser aufrufen. Die physischen Controller verbinden sich automatisch.

Ausfallsicherheit: Die Client-Firmware implementiert eine dynamische DNS/mDNS-Namensauflösung zur Broker-IP-Ermittlung, um Verbindungsabbrüche im lokalen Netzbetrieb zu minimieren.

Zusammenfassung

Das AALeC-Quizsystem kombiniert hardwarebasierte Eingabegeräte (IoT-Controller) mit standardisierten Backend- und Webtechnologien. Durch die lokale Ausführung und den Einsatz des MQTT-Protokolls wird ein latenzarmes, netzwerkunabhängiges System für Gruppenabfragen realisiert.
